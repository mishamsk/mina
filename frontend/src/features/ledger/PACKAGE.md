# frontend/src/features/ledger

## Purpose

- Owns shared transaction browsing, detail, and entry workflow UI.

## Implicit Contracts

- REST transaction responses own classes, shapes, roles, display titles, and amounts; every transaction surface uses the display title, and contextual overflow tooltips include current account FQNs. Shared views must not derive totals, and unavailable USD renders as `N/A`.
- Transaction pages are disposable in-memory snapshots keyed by normalized request parameters, including a future date anchor while paging its projected sequence. Keep a displayed snapshot during a failed refresh, discard responses superseded by a newer page generation or background refresh for the same page, preserve errors created after an ordinary load began, and do not let detail or entry-only URL changes orphan an equivalent request.
- Entity-filter reference lookups share one lifecycle guard that aborts on Back and unmount and rejects completions from another pathname.
- Ledger lookups are a shared app-wide snapshot; a route that starts their load must let the result publish after unmount so route-independent editors cannot inherit a stranded loading state.
- Routes own the DSL `filter`, standing `class`, search, sort, pagination, and future-anchor URL semantics, including preservation of an explicitly empty `filter` while other list state changes. This feature owns only the composable `transaction` detail parameter, preserving unrelated parameters and fetching a selected persisted transaction absent from the current page snapshot; response-local recurring projections open from their list record without a URL parameter or detail fetch. List-state writes retain one overlay history entry so Back dismisses detail onto the updated list state, and a terminal lookup failure releases detail loading so the shared panel can render its reference-light fallback.
- Transaction-page snapshots include the selected sort field, direction, and browser-default Expected inclusion in their identity; the browser explicitly requests every lifecycle only when its URL has no expression. Date jumping is available only for initiated-date descending order and accepts server-projected future recurring rows. Projected rows render as Expected and open their response-local record in read-only detail; only the server-marked next projection offers definition-level Confirm next and Defer, while later projections have no actions. Date jumping retains button identity while loading so completion restores focus to the activated control. Closing the class popover restores focus without opening its trigger tooltip; closing the sort popover restores focus to its trigger unless an outside interaction targeted another control.
- Detail is read-only and follows the [transaction detail disclosure rules](../../../../docs/webui-design.md#transactions). Reopening its transaction row closes it through the row activation path without a competing outside-pointer close and restores focus, while register embeddings may keep the same transaction open as focus moves between its records. URL-first detail selections focus the panel; register row selections keep row focus while walking across transactions. An intentional newer focus target wins over deferred panel autofocus, source-seeded recurring editors count as inside the detail overlay boundary, and embeddings must retain the list restore target and transaction-row/pagination hooks used when a changed row disappears.
- Detail resolves recurring provenance through exact occurrence reads or the projection's active definition, shares the loaded projection definition with its Defer dialog and retries a failed projection read when Defer opens, links active definitions to editor-opening management routes, and renders cancelled definitions without a dead link or hiding the transaction while provenance loads.
- Register lifecycle refreshes may retain the complete replacement transaction while invalidating dependent register pages so detail stays complete without a redundant fetch.
- Category/Tag report previews reuse browser rows and read-only detail without paging, Edit mode, row mutation actions, sticky scrolling, or browser controls.
- Transaction rows and detail consume one applicability matrix and follow the [transaction action-placement rules](../../../../docs/webui-design.md#transactions). Materialized expected occurrences confirm through one actual-date dialog whose default is the scheduled date; list, transaction detail, and register detail submit the same value, and REST owns date-domain validation. Materialized-occurrence confirmation and projection-defer refreshes retain the displayed transaction snapshot while their pending dialogs stay mounted. Row and detail Confirm next actions share a route-stable disabled state through refresh, retain the displayed transaction snapshot, scope failures to the invoking projection or a warning after its detail closes, and reconcile response-local detail only while the confirmation source remains selected. Both definition-level projection mutations reuse definition invalidation; Defer retains its broader same-definition reconciliation because an offset can remove another open projection. A recurring-editor overflow launch dismisses its menu before transferring focus into the editor.
- Recurring-definition capture copies active reusable records in response order without dates, settlement, provenance, transaction identity, or transaction-only metadata.
- Edit-mode selection is page-local. Account Replace follows the [Transaction Edit mode workflow](../../../../docs/webui-design.md#transaction-edit-mode); ranked search supplies bounded source and replacement candidates, local choices remain visible across searches, and the ordinary replacement submission authoritatively revalidates current transaction eligibility. Completed counts drive feedback, affected account caches are invalidated from selected snapshots plus the explicit replacement, and the current-page refresh replaces per-transaction detail reads. A failed or superseded post-replacement page refresh clears the affected selection and leaves the current page stale for retry instead of republishing stale source choices; retained inline amount conflicts block replacement so their winner-backed snapshots cannot be superseded. Apply other narrow record mutations only to eligible record roles; other structural changes and full transaction replacement remain in the entry editor. Row-amount editing replaces the complete active transaction atomically, preserves record identities and the loaded ETag, and keeps invalid or failed input inline.
- Transaction editor baselines carry record IDs, retained hidden valuations, and the timestamp-backed ETag through shorthand, advanced, split, and amount-edit transformations; stale refreshes replace hidden baselines with the winner so retries cannot restore superseded values. Retained records omit provenance, new records omit identity, and imported records remain fixed identity anchors that cannot be split, merged, or removed.
- Concurrent replacement behavior follows [the transaction-entry stale-write UX](../../../../docs/webui-design.md#transaction-entry). Ledger owns the winner-backed editor baseline and retry gate, restores a cancelled winner only on the explicit conflict retry and requires review of the restore response before replacement, keeps shorthand tabs unavailable after structural recovery, pins retained inline-conflict rows outside cached query membership, prevents pagination from unmounting a retained inline draft, reapplies the query with row-removal focus fallback on discard, maps Advanced drafts onto winner identities, and never downgrades a newer in-memory transaction snapshot.
- Successful transaction mutations use the shared refresh helpers: invalidate affected reference and register snapshots, including every loaded transaction version in a conflict retry and explicitly identified accounts not present in available transaction snapshots; refresh the current transaction view, featured balances, and overview; and mark sibling transaction pages stale before the refresh can republish the current page. Recurring-definition invalidation also reloads provenance retained by a mounted transaction detail.
- Recurring-definition mutations advance occurrence catch-up before marking transaction pages stale; mounted browsers keep their snapshots while materializing newly due occurrences and refetching. A failed post-mutation catch-up clears transaction pages and reports the successful mutation with incomplete refresh instead of leaving an actionable stale projection. Deferring a projected row reconciles open response-local detail from the same definition against the refreshed page, closes removed projections, restores row focus to the refreshed next projection, and leaves other definitions untouched while refreshing mounted recurring-definition snapshots.
- A failed date-jump preflight leaves the current page visible and attaches retry feedback to that retained page; after an anchor is established, page failures and retries remain scoped to the anchored sequence.
- Background page refreshes preserve the mounted snapshot, serialize same-page results so superseded callers observe the winning refresh, synchronize page-local selection snapshots from successful same-page results, and expose row-visibility completion callbacks to their workflow owners.
- When an action refresh remounts its source row, focus restoration re-resolves the live overflow trigger; confirmed occurrence rows restore by transaction identity after date reordering, and row-origin projection confirmations update open detail without stealing restored row focus. Removed rows use the prior index or pagination fallback without a competing detail-panel cleanup target.
- Entry drafts persist only UI form values per tab. Initialization defaults neither create a draft nor overwrite entered values or take focus after interaction.
- Entry modal closure prefers an explicit stable launch target over transient pointer targets, then falls back to the owning list region and Transactions navigation.
- The entry modal's recent-transaction rail is passive, remains outside the tab order, and exposes account-title context without adding controls.
- Entity pickers call entity-specific ranked-search loaders with `limit=6`, and the multi-picker has no local-options mode; backend contexts own eligibility, candidate hidden policy, groups, matching, bounds, order, and returned entity detail used by caller-owned draft transformations. The shared picker owns selected options, exclusion IDs, stale-response rejection, debounced remote search, hierarchy/query interaction, option-shaped initial loading skeletons with visually stable retained result snapshots during refetch, retry UI, narrowing feedback that swaps atomically with its result snapshot, and selection without rescoring returned rows; valid typed parent paths scope their child request directly rather than depending on the parent group fitting inside bounded results, confirmation flushes a pending debounce and applies only after the matching rows arrive, closed blank pickers defer loading until opened, multi-picker results prefer the collision-aware top side so their complete non-scrolling result set stays viewport-bound above selected chips, and Retry restores focus to the combobox before its control unmounts.
- Hierarchical picker rows and locally resolved selected values show the complete FQN first and append a differing effective display title in muted parentheses. Current remote rows replace earlier query results, while caller-provided aggregate lookup fallbacks, detail reads limited to selected IDs absent from those fallbacks after a brief in-flight lookup grace period, and locally retained choices preserve active selected presentation independently of bounded matches and initial search failures.
- Picker-created entities remain local overlays until shared lookups refresh; creation-enabled Account, Category, and Tag call sites compose a separate advisory availability read for the complete typed FQN, surface advisory failures through the picker retry affordance, and leave REST create mutations to repeat authoritative path validation.
- A filter editor resolves exact human-readable entity selections only against active lookup rows so reused names and FQNs never bind to tombstoned predecessors, while new picker selections retain their returned ID and effective title for local presentation and serialize from the entity-specific picker response even if the aggregate lookup snapshot is unavailable. Stable-ID literals retain their literal URL value, display a matching active or tombstoned label when available, render as separate removable controls independently from same-text human picker selections, and remain removable when unresolved. The editor retains its own selected hidden entities while `Include hidden` is off; hidden selections from other rows or operators do not become available choices.
- Currency filters offer active account currencies plus typed codes, serialize canonical values into the DSL expression, and leave definitive code validation to REST. Deselecting a currency restores its surviving checkbox or moves focus to code entry when that checkbox disappears.
- Transaction filter controls follow the owning [filter-bar interaction and display contract](../../../../docs/webui-design.md#tables-and-filtering); routes own their URL semantics.

## Boundaries

- Owns: ledger display components, transaction snapshots and refresh coordination, detail loading, edit-mode behavior, entry UI mapping, and picker interaction/adapters.
- Does not own: generated API setup, accounting validation or persistence, route filter semantics, or the app-shell-owned `entry` URL lifecycle and entry-save orchestration.
